# Bluebird · 整站设计提案 V2

日期：2026-09-05。状态：**待用户审阅；不是已实施的产品规范**。

本轮交付是棋子概念、整站交互草案和实施计划。生产页面、分析算法与现有棋子均未替换。先迭代设计，用户确认后再执行生产实现。

## 1. 本轮方向

保留上一稿用户认可的左右布局与主要审计判断，重做棋子及作品气质的表达。上一稿使用的 Unicode 棋子不作为基线；当前 `react-chessboard` 实际 SVG 棋子才是质量对照。

主基调来自《リズと青い鳥》：窗光、细线、半透明水彩、温和的蓝与纸白、人物与空间之间的距离感。辅以《響け！ユーフォニアム》的乐器质感、练习室和少量黄铜色。

“窗边的一盘棋”是这次设计的内部主题，不自动替换现有产品名称 Open Chess Review。青鸟、羽翼和乐谱可以明确出现；具体出现位置和强度通过本轮草案审阅。这更新了上一份审计中对具象装饰更克制的建议。

## 2. 棋子：两条可比较的路线

### A · 窗光 / Windowlight（建议默认）

偏二维动画原画的轮廓，乳白与水彩蓝，较大的明暗色块。细节集中在主教的羽翼切口和马的羽片形鬃毛，适合长时间复盘。少量黄铜只用于王与后的颈环。

### B · 羽瓷 / Feather porcelain（可选主题）

更饱满的瓷器体积、深蓝釉面、羽毛纹样与黄铜环。作品意象更明显，适合大棋盘与分享卡；小棋盘是否过于复杂需要审阅。

草案可以在 A、B、当前 SVG 三套之间切换。两张生成图是**概念资产**，还不是最终独立棋子文件。草案以原图透明通道与定位显示每枚棋子；正式实现前必须统一轮廓、尺度、描边和基线。

| 棋子 | 固定的识别特征 | 作品意象 | 正式绘制目标高度 / 格子 |
| --- | --- | --- | --- |
| 王 K | 最高、清楚十字冠 | 窗光折面、极少黄铜 | 86% |
| 后 Q | 与王不同的开放冠形 | 轻微花瓣节奏 | 79% |
| 车 R | 平顶、三段城垛、宽塔身 | 乐谱平行线，只做少量内纹 | 68% |
| 象 B | 水滴冠与明确斜切口 | 羽翼负形，延续 Blue Bishop | 75% |
| 马 N | 马嘴、耳朵、弯颈一眼可读 | 羽片形鬃毛 | 74% |
| 兵 P | 圆头、短颈、最简洁轮廓 | 纸白与微蓝反光 | 53% |

白方保持暖白主体与蓝灰外轮廓；黑方保持足够深的蓝色主体。棋子颜色不承担当步质量含义。落子质量仍使用项目现有 V3 图标和语义。

棋子验收：

- 在 32 / 40 / 56 / 72px 格子、浅格与深格中分别检查双方六子。
- 王/后、象/兵、马/象不混淆；黑白双方在灰度下仍可区分。
- 普通状态、选中、上一着、将军、质量徽章、升变选择、箭头覆盖均可读。
- 统一底座、视觉重心、边距；王冠和马鬃不会被格子裁切。
- 5 名用户辨认两方六种棋子，至少 4 人无需提示完成；这是拟定标准，尚未测试。
- 如概念纹理在小尺寸下失真，先减少纹理并加固轮廓，再决定是否提供小尺寸专用资产。
- 最终优先手工整理可维护 SVG；如果保留水彩栅格材质，提供独立透明 WebP/PNG 与足够的像素密度。不要把生成整张图直接当成生产精灵图。

## 3. 视觉系统

| 角色 | 建议色值 | 用途 |
| --- | --- | --- |
| 暖纸 | `#f8f6ef` | 页面底色，减少原版偏黄感 |
| 纸白 | `#fffef9` | 阅读内容、输入区域 |
| 墨蓝 | `#2d4654` | 正文、主标题 |
| 次级墨色 | `#566e78` | 次要说明；实际对比度随背景验收 |
| 窗边蓝 | `#627fa2` | 主行动、当前页面、品牌呼应 |
| 浅格 | `#eee8d9` | 棋盘浅格 |
| 青瓷深格 | `#b1c6c2` | 棋盘深格，承托蓝色棋子 |
| 玻璃蓝灰 | `#d6dfdc` | 分隔与轻边框 |
| 干燥玫瑰 | `#d3b4bb` | 小范围章节提示，不做正文 |
| 旧黄铜 | `#b7a270` | 页码、书签、少量装饰，不改质量颜色 |

这些是提案变量，尚未写入生产 tokens。当前亮色主题先完成，深色主题另做实际审阅，不机械反色。

标题用有书页感的衬线，正文和棋谱用清楚的无衬线；SAN、评估数字使用等宽数字。正文 14–16px、次要信息 12–13px，不能靠浅灰和微小字号制造“空气感”。以 8px 为间距基础，4–8px 小圆角；留白集中在章节之间。

艺术密度：

- 首页：可看到完整窗光、青鸟、练习室物件，负责建立记忆。
- 复盘：以棋子、棋盘、细线和轻纸色表达主题，阅读区保持稳定。
- 学习：像展开的一页笔记，水彩小幅进入页眉。
- 训练：像练习页，题目和棋盘优先，反馈温和明确。
- 棋谱库：目录与书签的节奏，便于找回记录。
- 设置：清楚、低干扰，保留产品气质。

声音沿用当前默认和用户设置，不自动播放音乐。动作以 120–180ms 局部变化为候选，遵循 reduced-motion；不循环飘落羽毛。

## 4. 整站结构与关键页面

主导航：新复盘 / 棋谱库 / 训练；当前棋局内部切换复盘 / 学习 / 引擎。设置在全局入口。沿用现有路线职责，不改 canonical analysis 数据模型。

| 页面 | 首要任务 | 草案结构 | 后续需完整覆盖的状态 |
| --- | --- | --- | --- |
| 首页 / 导入 | 快速开始一盘 | 简短标题 + PGN/FEN 输入 + 示例入口；右侧艺术与示例棋盘 | 首访、最近棋局、输入错误、文件导入、分析中、取消/重试 |
| 复盘 | 理解当前一步 | 左侧大棋盘与导航；右侧“这一着 / 整盘”；整盘含评估曲线、准确度与关键节点 | 分析中、部分完成、终局、分支、升变、重算、无可用服务 |
| 学习 | 看懂原因与后果 | 当前局面 + 一段观察 + 可走的变化 + 一个练习入口；证据按需展开 | 基础讲解、生成中、无生成式服务、依据不足、讲解失败 |
| 引擎 | 查看客观候选 | 复用同一棋盘，展示引擎设置、候选与 PV | 启动、计算、停止、不同深度与 MultiPV、错误 |
| 棋谱库 | 找回并继续 | 搜索/筛选、棋局列表、分析状态与继续入口；首访为空目录 | 无记录、少量、长列表、导入冲突、存储空间问题 |
| 训练 | 将理解变成练习 | 今天要练的主题 + 单题棋盘 + 提示/答案；完成后给下一步 | 记录不足、可训练、作答、再试、完成、历史复习 |
| 设置 | 清楚控制能力和数据 | 外观与语言、分析、增强服务、数据管理分组 | Browser Core、本地增强未连接/可用、备份/恢复、清除确认 |
| About / Privacy / Feedback | 建立可信边界 | 简明介绍、实际数据流说明、明确反馈渠道 | 按实际部署配置编写并核实 |

### 复盘的阅读顺序

1. 当前走了什么：SAN + 项目原有质量图标与标签。
2. 最值得看的一件事：一段简洁且可追溯的解释。
3. 变化会如何发生：在同一棋盘查看，保留返回主线。
4. 为什么这样评价：点击展开引擎、分类证据；Maia 与教练分别注明来源。
5. 想看整盘时再切换总结；**timeline 保留在右侧整盘总结内**。

Stockfish、Maia、LLM 仍明确区分，不合成无解释的总分。Human difficulty 不变成官方 Elo，LLM 不编造棋类事实。概念中所有示例数值/文字都标注为演示，不表示重新跑过完整分析。

### 响应式草案目标

- 1280×720：压缩多层标题，棋盘优先尝试 420–460px；棋盘、玩家与走子控制在首屏可用。
- 1440×900：棋盘约 500–540px，右栏约 400–500px，保持阅读行宽。
- 更宽屏幕：限制正文宽度，留白用于分隔，不无限扩张右栏。
- 平板：保留棋盘优先，当两列不足时转单列。
- 手机 390px：首页操作在艺术图之前；复盘是棋盘 → 走子控制 → 局部内容切换；不强塞三列。
- 首要触摸目标约 44px；键盘操作、焦点与屏幕阅读器标注纳入验收。

草案内“手机宽度”只模拟内容容器，不能代替真实 Safari/Chrome 手机验收。

## 5. 草案审阅方法

交互草案包含首页、复盘、学习、引擎、训练、棋谱库、设置及棋子样张；使用统一的双排棋子概念资产。可切换两套新棋子与当前棋子作比较。

建议按这个顺序审阅：

1. **棋子样张**：先看 A 与 B 的轮廓、材质、作品联想，再在棋盘里判断密度。
2. **复盘**：看左右比例、走子、当前一步与整盘总结，确认持续使用是否舒服。
3. **首页 → 学习 → 训练 → 棋谱库**：确认这些页面是否属于同一个产品，学习路径是否自然。
4. **手机宽度**：确认信息顺序；正式开发后再实机验证。

本轮最有价值的反馈是：棋子偏 A / B / 两者融合；主题表现需要更明显还是更克制；哪个页面比例仍不舒服。无需本轮逐个批准色值和间距。

## 6. 审阅后的实施顺序

| 阶段 | 工作 | 交付与通过条件 |
| --- | --- | --- |
| 设计迭代 | 按本轮反馈修棋子和页面，不改生产代码 | 确认一套默认棋子、艺术强度、复盘比例与页面结构 |
| S1 视觉基底 | 正式独立棋子、tokens、字体层级、通用布局 | 小尺寸棋子样张通过；现有质量图标和棋类语义保持一致 |
| S2 核心闭环 | 首页导入、复盘、Study、Training、History | 导入 → 关键一步 → 学习 → 练习 → 找回记录可完成 |
| S3 上线缺口 | 修审计 W01–W07；公开能力和数据边界清晰 | API 输入验证与资源限制、数据清除覆盖、备份恢复、服务降级完整 |
| S4 发布验证 | W08–W09、生产构建、多浏览器、性能、错误与反馈入口 | 可审阅的 Web beta 候选；发布说明、监控和回滚步骤可执行 |

S2 与 S3 在适当的逻辑变更中一起落实，不能只换皮后宣称可上线。详细工程事实以 [上一轮审计](../audits/2026-09-05-web-launch-and-art-direction.md) 为准。

首发范围沿用复盘与学习平台：Browser Core 的 PGN/FEN、Stockfish、分类、准确度、阶段、开局、图表、浏览器内记录。增强 Maia/生成式 Coach 按实际可用服务提供。多人对弈、匹配、赛事和云端社交账户不自动加入这轮。

完成设计确认不等于发布授权；先做可审阅的实现、测试与预览，再按用户后续指示发布。

WebP 是保留原尺寸与透明通道的展示编码；本轮没有用图像处理程序重画、裁剪或修改生成图内容。

交互草案使用演示局面与演示讲解，不连接引擎、账户、真实服务，不保存用户棋谱。草案里的设置只改变当前预览。生产测试结果仍以此前审计的实际执行记录为准，本轮不因为新增设计文档重复宣称代码已验收。

本轮设计验证：JavaScript 语法检查通过；33 ply 由项目已安装的 chess.js 逐步验证，Qb8+ 后唯一合法应对为 Nxb8，Rd8# 后为将杀；浏览器中完成了 Qb8+ → Nxb8 → Rd8# 的训练交互。已查看两套棋子在样张中的实际效果，以及桌面复盘、首页和 390px 内容容器的复盘布局；首页、学习、引擎、棋谱库、设置、棋子样张在 390px 内容宽度下未出现横向溢出。这不代表已经完成真实移动设备测试、用户辨认测试或生产引擎分析。
