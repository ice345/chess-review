# 错误回顾 UX 审计与实施指导

日期：2026-09-12。供产品审阅及后续 AI 实施使用。

## 1. 结论与审计边界

**当前问题不只是布局，更主要是：练习已经开始，页面却仍然像普通复盘。** 原棋盘内练习这个方向是正确的，不需要换棋盘库或照搬 Lichess 三栏布局。应先补齐模式切换、棋盘反馈、结果统计和异步状态，再调整信息层级。

保留现有棋子、棋盘颜色和整体色调。此次只交付报告，不修改应用，不替现有未提交改动做验收背书。

审计对象是 `9f7b887` 加当前工作区的未提交代码，包含新 `RetroPractice` / `useRetrospect`。旧弹窗组件已在工作区删除，因此不能按旧弹窗版本制定修复计划。后续实施者必须重新检查 Git 状态，不要覆盖、混入或提交其他人的改动。

证据分为：

- **已确认**：用户截图与当前源码可以直接支持。
- **待复现风险**：代码存在相关路径，但本轮没有在浏览器中实测。
- **设计建议**：期望行为与验收标准，不代表当前已经实现。

本轮进行了截图分析、源码与现有测试阅读、Lichess 上游源码对照。没有运行应用、测试、生产构建或 NUC 压测。本报告不是完整安全审计或上线认证；对平台其他部分给出的是有边界的上线复核清单。

## 2. 三张截图说明了什么

### 图一：入口像设置表单，缺少练习价值与身份

标题、说明、下拉框、复选框、大按钮横向并列，缺少视觉组织。用户首先需要知道“这是我的哪一方、几道题、点了会发生什么”，而当前最显眼的是通用设置和 Start practice。连续分隔线也增加了粗糙感。

这不是棋子或配色造成的。保留颜色，缩短文案，把数量和棋手身份放到入口，把可选设置收起，就能明显改善。

### 图二：练习状态与普通复盘状态同时出现

上方要求为白方改进 Qf4，下面却显示 `46. Ne5 · Good`、Accuracy、解释入口、分析来源和整局摘要。棋盘仍有上一手质量徽标和评分条。用户难以判断当前到底是在看 Ne5，还是在解 Qf4 的题。

其中有两个不同问题：

1. **上下文竞争**：上一手数据可能本身有效，但不应该在正在作答的练习旁担任主要信息。
2. **步号错误**：源码直接显示 `move.ply`。截图棋盘下方是 `23... Ne5 / 46 ply`，卡片却写 `46. Ne5`。ply 是半回合索引，不是棋谱回合号。

### 图三：应学习任务反馈，不必复制整个站点

图三的 Lichess 已经处于“好着”的成功状态，显著的勾和 Continue 共同告诉用户下一步做什么。它不能单独证明启动阶段的画面；原错棋箭头和失败回退可以从上游代码另外确认。

你提到的“放在双方之间”，适合落为**右侧双方摘要附近、与所选棋手关联的练习入口**。不建议把大按钮盖在棋盘中央。Lichess 的聊天栏与导入信息栏不必移植到我们的复盘产品。

## 3. 当前值得保留的基础

- 已经复用原棋盘落子；成功或查看答案后可以继续探索变例。
- 已有原错棋前的局面、原错棋 UCI、最佳着及引擎证据。
- 已在部分分析、Maia、Study、Coach 展示中隐藏答案；不是完全没有防泄漏措施。
- 引擎失败已有“不判错”的处理；候选列表之外的合法着可以调用 Stockfish 检查。
- 棋盘已有 `animationDurationInMs: 160`，不是缺少动画能力。
- 已有浏览器模式和相应端到端测试；不能把 Maia/LLM 变成练习依赖。

因此建议增量完善现有实现，不重新建一个独立练习棋盘或复制分析逻辑。

## 5. 推荐布局：保留两栏，明确切换任务

### 5.1 普通复盘：把入口与棋手摘要放在一起

```text
┌────────────────棋盘─────────────────┐  ┌────────复盘侧栏─────────┐
│ 对手信息                            │  │ 关键时刻 / 当前着法     │
│                                     │  │ 双方摘要               │
│             原有棋盘                │  │ 白方 ice-345           │
│                                     │  │ 2 次失误 · 1 次漏着     │
│ 自己的信息                          │  │ [ 回顾白方的 3 个局面 ] │
│ 棋谱导航                            │  │ 黑方摘要               │
└─────────────────────────────────────┘  │ 筛选设置 ▾             │
                                         └────────────────────────┘
```

示意数量仅为设计例子。入口实际题量来自 canonical `practiceMoves`，不能简单相加标签数量：同一着可能有质量标签和漏杀注释，且部分局面不适合出题。

已关联账号且棋手身份可靠时默认该方；导入棋局无法识别时明确让用户选白/黑。不要把“棋盘朝向”当作“本人身份”的可靠证据。筛选包含 inaccuracies，显示选择后的真实数量。零题时区分“没有相应错误”“引擎证据未就绪”“部分局面已排除”，允许回到复盘或选择另一方。

### 5.2 开始后：侧栏成为练习工作区

```text
┌────────────────棋盘─────────────────┐  ┌────────练习中───────────┐
│ 对手信息                            │  │ 错误回顾  1 / 3  [退出] │
│                                     │  │ 白方走 · 第 24 回合     │
│      原错棋前局面 + 原错棋红箭头     │  │ 原着 24. Qf4 · Mistake  │
│                                     │  │ 找到更好的走法          │
│ 白方走 · 请直接在棋盘落子            │  │ 红箭头表示原来的错棋    │
│ 自己的信息                          │  │ [提示] 查看答案  跳过   │
└─────────────────────────────────────┘  │                        │
                                         │ 回答后在此展示结果证据  │
                                         └────────────────────────┘
```

“提示”是建议新增能力，可先只实现高亮可考虑的棋子；不得用 LLM 随机生成战术提示。第一版也可以没有提示按钮，但必须有明确开始状态、失败反馈、查看答案和退出。

成功后同一区域变为：明显的勾 + “这步保持了局面” + 用户实际走法 + 宽主按钮“下一题”。最后一题使用“查看本次结果”。原题号在点击下一题前保持不变。不是唯一最佳着也可正确，文案不要误称“你找到了唯一最佳着”。

### 5.3 信息显示策略

| 信息 | 普通复盘 | 等待作答 / 判定 / 回退 | 成功 / 查看答案 |
| --- | --- | --- | --- |
| 原棋盘、棋手信息 | 显示 | 显示 | 显示 |
| 原错棋箭头 | 按复盘规则 | 显示，尝试动画期间可淡出 | 默认隐藏，可手动对比 |
| 最佳着 / 引擎 PV / Maia 候选 | 按用户选择 | 隐藏 | 按需展开，并匹配当前局面 |
| 评分条与数值 | 显示 | 隐藏数值及比例，保留尺寸避免跳动 | 显示当前探索局面的正确分数 |
| 普通上一手质量徽标 / 裁决卡 | 显示 | 隐藏 | 用本题结果取代，不继续显示无关上一手 |
| 整局摘要、图表、来源切换 | 显示 | 从主任务区收起 | 次级区域或返回复盘后显示 |
| 练习题号 / 状态 / 退出 | 无 | 始终可见 | 始终可见 |
| AI 教练 | 按需 | 不展示本题答案性内容 | 有结构化证据时按需请求 |

用统一的 `practicePresentation` 派生策略协调各组件，避免每个组件独立猜 `active` / `locked`。这是展示策略，不把分析算法搬入 UI。

跨 Review / Study / Engine / Coach 路由必须有一致约定：建议保留练习会话，离开题目则暂停，回来提供“继续本题”。需要看答案时明确转为查看答案或退出，不悄悄恢复引擎建议。已有相关隐藏与恢复测试应保留。该机制是学习辅助，不是防作弊系统；用户仍可另开分析工具。

### 5.4 手机与矮屏

手机采用“紧凑任务条 → 棋盘 → 反馈和操作 → 可展开证据”。开始时把任务条与棋盘带入视口，不能只是改变页面下方文字。避免手机上把长成功解释放在棋盘前，迫使每题滚动。

桌面沿用棋盘加侧栏；建议侧栏可读宽度约 320–400 px，具体随现有容器适配。1280×720 下优先保障完整棋盘和当前任务，摘要不占第一屏。不要为模仿三栏牺牲棋盘面积。

避免固定底栏遮住升变选择或棋盘底行。允许长文本正常滚动；必要时任务状态固定在侧栏内，不能制造两个同时滚动的操作区。

## 6. 交互实现：从“文字变化”变成完整反馈循环

### 6.1 原错棋箭头

已有 `faultUci` 和 `fenBefore`，无需新增搜索。从经过合法性验证的原错棋生成箭头，并使用现有错误语义色。文字同步说明“红箭头是你当时走的棋”。

箭头来源需区分：原错棋、引擎建议、用户绘制、练习尝试。作答时只保留允许的类别，不能继续用一个 `[]` 全部清空。方向由棋盘坐标系统负责，不能手算屏幕位置；测试黑方朝向、翻转、升变和王车易位。王车易位的箭头说明国王移动即可，不把两个箭头误当两种答案。

提示启用后，原错棋与提示必须可区分，不应同时出现多个语义不明的红绿箭头。若用户标注可能透露答案，可在作答时暂时隐藏，并在退出恢复。

### 6.2 推荐状态机

```text
idle → preparing → solving → evaluating → accepted → next / complete
                       ↑          │
                       │          ├→ rejected → rewinding ─┘
                       │          └→ unavailable → 可重试
                       └──────── retry
solving → revealed → next / complete
solving → skipped → next / complete
活动状态 → paused → resume
活动状态 → exit（取消请求并清理计时器）
```

这是建议的显式状态契约，实际可用 reducer，不要求引入状态机依赖。不要用多个互相矛盾的布尔值拼状态。

每次尝试记录 `sessionId`、`exerciseId`、`attemptId`、`promptFen`、`attemptedFen` 和 UCI。只接纳仍属于当前尝试的结果。清理时中止请求和动画计时器；中止信号之外仍需身份校验，防止不响应 abort 的异步源污染下一题。

### 6.3 错误落子的可见回退

1. 用户合法落子，先让棋盘提交尝试后的局面。
2. 判定期间显示“正在检查这步”，阻止重复落子，保留取消/退出。
3. 如果失败，显示失败图标和“再试一次”，暂时保留刚走出的棋。
4. 再把棋盘目标位置改回题目初始局面，让现有棋盘动画完成回退。
5. 回退结束后重新允许落子，原错棋箭头恢复。

建议普通模式失败停留约 300–500 ms、回退约 150–220 ms；这些是待交互验收的设计参数，不是 Lichess 的已验证时长。必须覆盖原错棋的同步快速路径和命中缓存路径，不能只在慢引擎时看到动画。

`prefers-reduced-motion` 下取消位移动画和强制延迟，仍用清晰文字/图标反馈。定时器结束前退出或换题，绝不能把新棋局倒回旧 FEN。非法走法只提示不能这样走，不记录为有效错误答案。

### 6.4 判题证据与不确定性

当前代码 `PRACTICE_MAX_WIN_PERCENT_LOSS = 4`，是练习接受标准，不等于客观质量标签。保留现状，不能顺手调整 Accuracy、WinPercent、分类、Great/Brilliant 或难度算法。

针对 depth 12 与已存根分数可能不一致的问题，先编写边界复现用例，再定义判题策略：使用相同起始局面、历史、引擎版本与明确搜索预算；必要时在同条件下重新获得基准与候选分数。记录证据元数据，避免不同版本/局面缓存混用。根最佳着必须与对应分数/PV 有明确关联，不能盲信列表第一个元素。

候选不在 MultiPV 中不等于走错。超时、引擎不可用、证据不足均为“暂时无法判定”；允许重试、查看答案或跳过，不增加失败次数。建议设置有界等待，例如先以 15 秒为可配置软超时，再用低端设备测量调整，不承诺所有题固定秒数完成。

如改变判题语义，必须应用仓库 `chess-analysis-change` 技能，更新确定性测试与 `docs/mistake-practice.md`，在独立 commit 中说明，不混进 CSS 调整。

## 7. 练习结果与学习闭环

队列进入会话时生成稳定题目 ID 和顺序。建议结果记录包含：局面/棋局标识、算法与引擎版本、原错棋、结果、有效尝试次数、是否提示、完成时间。不要仅存一个 `solvedPlies`。

| 字段概念 | 含义 |
| --- | --- |
| currentIndex | 当前题序号，与完成数量独立 |
| processed | 已处理，不再自动出现在本轮队列 |
| solved | 用户自己走出被接受的答案 |
| assisted | 提示后走出答案 |
| revealed | 直接看了答案 |
| skipped | 跳过，可在本轮结束后重试 |
| unavailable | 证据不足或引擎失败，不是能力判断 |

结束页示例：“回顾了 5 个局面：独立解出 2、提示后解出 1、查看答案 1、跳过 1。”主按钮“重试未独立解出的局面”，次按钮“返回复盘”。不要宣称一次成功就是永久掌握，也不要把此结果换算为正式 Elo。

第一版可以只保存会话内结果；跨刷新续练和间隔复习放下一阶段。持久化时使用现有本地数据层，补充备份、恢复、清除数据和分析版本失效策略。不可另建一套无备份的 localStorage 孤岛。

成功解释顺序：用户这一步为何可接受的 Stockfish 证据 → 原错棋的关键损失 → 可选 Maia“为什么人容易这样走” → 按需教练。缺少战术证据时只展示已验证变例与分数，不让 LLM 发明“弃子牵制”等理由。

| 批次 | 内容 | 主要文件 | 完成条件 |
| --- | --- | --- | --- |
| A：正确性 | 结果分离、稳定题号、真实步号、排除原因 | `use-retrospect.ts`、`retro-practice.tsx`、`current-move-verdict.tsx`、canonical 题目选择模块 | 独立解出/查看/跳过不混淆，黑方/FEN 起点编号正确 |
| B：任务布局 | 棋手摘要入口、练习侧栏、统一显示策略、移动端次序 | `review-route-panels.tsx`、`review-runtime.tsx`、`retro-practice.tsx`、现有样式文件 | 点击即有清晰状态；无上一手裁决和答案信息竞争 |
| C：棋盘反馈 | 原错棋箭头、尝试局面、回退、退出恢复 | `review-shell.tsx`、`use-retrospect.ts` | 快速失败与慢失败都可见；黑方与减少动画设置正确 |
| D：异步判题 | 请求身份、取消/超时、证据一致性 | `use-retrospect.ts`、必要的 analysis / Stockfish 接口 | 旧结果不串题；失败不误判；语义变化有文档和回归 |
| E：学习闭环 | 完成页、会话结果；后续持久化与重试队列 | 练习组件、现有库与备份层 | 结果可信且能再次练习，不损坏原棋谱 |
| F：上线复核 | 真实域名、NUC、缓存升级、恢复演练 | 既有部署脚本/文档及发布测试 | 产生新的可复核证据，而非引用历史通过次数 |

每批携带本批测试与文档，不把测试拖到最后。建议先 A，再 B/C；D 中的请求身份最好在 C 引入延时前完成。持久化 E 可以延后，不阻塞第一版易用的错误练习。

UI 不重算分类、WinPercent、理论边界；领域结果属于 `packages/analysis`，棋谱回合/合法落子使用 `packages/chess-core` 的规范数据。原复盘主线、评论和用户变例不因练习回退被删除。

## 9. 必须覆盖的验收场景

| 场景 | 预期 |
| --- | --- |
| 从页面较低处开始练习 | 棋盘与任务状态进入可见区，明确显示哪方走和原错棋 |
| 普通白方/黑方题，翻转棋盘 | 箭头指向正确格子，任务方不随视角误变 |
| 从黑方第 50 回合的 FEN 开始 | 标签为实际 `50...`，不能显示 ply 1 或错误白方编号 |
| 再走一次原错棋；缓存立即拒绝 | 能看到尝试与回退，状态可被辅助技术感知 |
| 未缓存的合法候选 | 显示判定中；不能因不在候选列表直接判错 |
| 两题，第一题答对但未点下一题 | 仍显示 1/2；点击后才到 2/2 |
| 直接看答案 / 全部跳过 | 不计为独立解出；结束页明确区分 |
| 引擎超时、初始化失败 | 未判定，可恢复；不增加错误次数 |
| 判定或回退中退出、切棋局、重启练习 | 无旧分数/旧 FEN/旧计数回写 |
| 升变、易位、吃过路兵、重复局面历史 | 棋规正确；历史用于判题；回退恢复原局面 |
| 解出后继续走变例，再退出 | 原棋谱与用户既有变例无损；返回约定上下文 |
| Review / Study / Engine / Coach 切换 | 练习暂停/恢复策略一致，没有无意泄露当前答案 |
| 0 题、理论排除、损坏/缺失引擎证据 | 文案解释实际原因，不卡死、不虚增完成数 |
| 320/390/768/1024 px、1280×720、1440 px | 无横向溢出，棋盘/状态/主操作可达，控件不遮棋盘 |
| 200% 文本缩放、键盘、减少动画 | 内容可读、焦点有序、状态播报不过量，不依赖颜色 |
| Browser Core 无 Maia/LLM | 完整完成练习；没有必须去启用本地服务的死路 |

现有 `e2e/mistake-practice.spec.ts` 已覆盖原地作答、查看/跳过、引擎失败、候选外搜索、答案隐藏、手机宽度等。新增测试应验证上述缺口，而不是只断言按钮存在。动画测试要观察尝试局面和回退顺序，不能只看最终 FEN。

实施时可使用的现有命令（本报告未执行）：

```sh
pnpm --filter @chess-review/analysis test
pnpm --filter @chess-review/web test
pnpm typecheck
pnpm lint
NEXT_PUBLIC_APP_MODE=browser-core pnpm build
pnpm exec playwright test --config playwright.release.config.ts e2e/mistake-practice.spec.ts
```

先运行相关窄测试，再运行相关包套件；集成变化需生产构建与浏览器验收。Enhanced Local 用对应环境单独验证，不将服务不可用伪装为通过。检查 Playwright 配置的服务端口和启动方式，避免影响用户正在运行的开发服务。最终审查 diff、生成文件和所暂存的文件。

## 10. 整个平台还应完善什么

下面是上线前应复核的具体工作，并非宣称这些功能全部缺失。9 月 11 日工作区已经包含 OAuth/代理边界、分享与注释、离线外壳、并行预算等改动；不能继续拿旧清单把它们写成“尚未实现”。

### 10.1 上线必须有证据的路径

1. **导入 → 分析 → 关键时刻 → 练习 → 返回棋局**：做成完整验收旅程。输入错误、部分分析、取消、刷新恢复都有可理解状态；不要只验收每个页面单独打开。
2. **真实 Cloudflare 域名**：验证授权成功、拒绝授权、过期会话、断开与重新连接，回跳不得落到容器地址；来源限制与 Cookie 同时覆盖 localhost 和真实 HTTPS。已有修复必须在目标部署复核。
3. **数据安全与恢复**：实际做一次导出、清空测试副本、恢复并核对棋局/注释/设置的演练。告诉用户哪些数据只在浏览器；服务器备份不会自动备份访客 IndexedDB。
4. **更新与离线**：验证老页面、老 Service Worker、新服务端混用时能恢复；WASM 使用不可变缓存时替换字节必须有资源版本策略。离线打开旧棋局不等于所有浏览器都能离线重新分析；现有文档已记录差异，产品表述必须一致。
5. **NUC 资源边界**：Browser Core 的 WASM 主要消耗访客设备资源，不能把所有访客分析都算到 NUC。NUC 重点测 Web/代理/导入；若同时运行 native Stockfish、Maia、Ollama，再分别测内存、队列和交互延迟，不默认全部同时运行。
6. **故障可诊断**：将服务不可达、外部平台限流、会话过期、来源拒绝区分显示，并提供可安全复制的错误编号。日志不得包含 token、Cookie 或棋局内容。先用现有日志，不必为上线引入付费监控。

建议在真实机器记录冷启动、单局分析、批量导入、交互判题的耗时分布与峰值内存，并做服务重启与回滚演练。当前报告不提供虚构的 NUC 并发容量。

### 10.2 上线后的产品优先级

- **P1 体验一致性**：统一回合号、空状态、按钮尺寸、术语和 loading/error 表达；让“复盘”和“练习”是清楚的任务。
- **P2 学习连续性**：未独立解出的局面重试、恢复上次练习、按问题类型筛选。等基本结果可信后再做间隔复习与趋势。
- **P2 解释质量**：让用户从关键时刻看到原错棋、可接受改进和证据；Maia/Coach 作为有来源的补充，避免成功页面又变成大型仪表盘。
- **P2 中文与无障碍**：先统一当前页面的中英文策略与翻译 key；棋盘键盘可用性需要实际核查，不能仅靠按钮 `aria-label` 宣称支持无障碍。
- **P3 扩展功能**：跨设备同步、更多开局探索或社交功能应有单独需求，不是这一轮上线必要条件。保持免费开源，不先引入付费墙或账号系统重构。
