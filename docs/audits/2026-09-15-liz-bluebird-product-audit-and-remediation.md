# Open Chess Review：美学、复盘体验与产品完整性审计及修复方案

日期：2026-09-15  
审计基线：`56d5af34e82f89a0652899c54dfe737331009736`  
目标：保留《リズと青い鳥》所启发的色调、空气感与克制，同时让复盘、分析、学习体验达到成熟棋类产品的可靠程度。  
交付性质：调查结论与可执行修复方案。本次没有修改产品算法或实现下文修复。

## 1. 结论

**当前项目已经有成立的美术方向和相当完整的复盘工具基础，但尚不能说“美学、体验、业务逻辑、整体性已经全面对标 Chess.com 和 Lichess”。**

准确地说：

- **美学方向成立。** Windowlight 的浅纸色、灰蓝、青瓷棋盘、细分隔线，以及 Feather Porcelain 棋子，已经形成统一语言。需要继续打磨的是视觉重心、阅读节奏和功能状态，而不是重新换一套主题。
- **电影气质只完成了部分转译。** 当前更接近温暖、整洁的棋谱笔记本。电影官方材料中更鲜明的冷暖光关系、纤细感、距离感、细微动作和安静张力，尚未全部进入产品的操作节奏。
- **功能覆盖已明显超出简单 Stockfish 前端。** 原地重试、引导关键时刻、变例、开局探索、残局库、Notebook、多局分析、训练队列、备份与离线能力均已有实现，不能继续把它们列作“从零补齐”。
- **最重要的差距是产品语义和任务闭环。** 提前结束却宣称已复盘全部关键时刻；完成摘要选材不够准确；旧分类投影仍影响教学统计；Training 与 Review 的阶段指标口径不清；复盘主操作竞争注意力。这些比颜色是否再浅一点更值得先修。
- **成熟度证据仍不充分。** 自动化覆盖是优势，但真实引擎异常排查、真实设备、读屏操作、真实缩放、生产部署和首次使用者测试，不能用截图或单元测试替代。

### 1.1 “对标”应分三个层次

| 层次 | 本项目当前判断 | 下一阶段目标 |
| --- | --- | --- |
| 复盘与分析工具 | 功能面接近，任务组织和信任表达仍有差距 | 一盘棋从导入到学会一个改进点，全程清楚、稳定 |
| 个人学习产品 | 已有多局画像和队列；训练入口、复习节奏、角色一致性尚需收束 | 用户知道今天练什么、为什么练、上次学会了什么 |
| 完整在线棋类平台 | 不等同于 Chess.com / Lichess | 对弈、匹配、赛事、社交、反作弊等应独立立项，不能通过本轮 UI 修复宣称完成 |

**推荐定位：有独立美学、解释可追溯、适合长期使用的复盘与个人训练工作台。** 不应把整个平台的全部功能都加入本轮修复范围。

### 1.2 本轮优先顺序

1. 先排查示例棋局中异常评价的来源，修复明确的结果/计数/状态问题。
2. 让 Review 每一屏只提出一个主要学习动作。
3. 打通“看见问题 → 自己重试 → 看懂原因 → 加入训练 → 下次复习”。
4. 提升文字、棋子和状态反馈的可读性。
5. 最后微调光感、字体节奏和辅助页面的一致性，并完成发布验收。

## 3. 官方参考：究竟应该继承什么美学

### 3.1 可核实的创作意图

导演在官方采访中强调真实、透明的空气感，以及个体之间细小变化的积累；同时谈到隔着玻璃观察人物般的色彩感受。这里的“透明”包含脆弱、距离和凝视，并不等于全界面透明背景。参见[山田尚子官方采访](https://liz-bluebird.com/interview/)。

西屋太志的官方评论强调纤细线条、教室中的紧张空气、轻微呼吸，以及日常交流中渐变的距离和情绪。参见[官方工作人员评论](https://liz-bluebird.com/news/?id=3)。

**以下为本审计的设计转译，不是官方制定的 UI 规范：**

| 原作参考 | 产品中的转译 | 不宜采用的替代方法 |
| --- | --- | --- |
| 透明、轻、纤细 | 清晰层级、轻边框、少量表面、简短文案 | 把文字整体降低对比度 |
| 冷暖光之间的关系 | 中性/微暖底色，局部蓝绿冷光，少量暖色强调 | 全部染成统一奶油色或统一粉蓝色 |
| 人物之间的距离 | 棋盘与解释之间稳定的关联、恰当的留白 | 把所有信息拉远，让用户反复寻找 |
| 微小动作的意义 | 选择、落子、回退、进入变例都有准确反馈 | 无功能意义的羽毛飘动、循环呼吸动画 |
| 安静但有张力 | 常态低噪声，真正关键的错误或唯一着法清楚突出 | 所有按钮、所有标签同等显眼 |
| 给观察留时间 | 用户控制揭示答案；说明按需展开 | 自动播放解释、默认展示所有最佳箭头 |

### 3.2 电影本篇、童话段落、官网不能视为同一套色板

官网首页可见鲜明的童话森林绿、天空蓝、花卉暖色；采访页的本篇配图则具有建筑、制服、日光与阴影的关系。它们共同支持轻盈的视觉印象，但不支持“整部作品就是低饱和米白”的简单概括。参见[官方网站](https://liz-bluebird.com/)及[采访配图](https://liz-bluebird.com/interview/)。

建议明确参考层级：

1. **复盘工作区：** 以本篇的日常空间、克制和观察感为主。
2. **首页、空状态、分享卡：** 可少量吸收童话段落的色彩生命力。
3. **品牌标记与棋子：** 延续已有原创视觉体系；不增加电影人物或场景贴图。

### 3.3 当前主题是否应该推翻

不应该。当前 token 是可持续的起点：

| 角色 | 当前值 | 判断 |
| --- | --- | --- |
| 页面 | `#f8f6ef` | 温暖、统一，可保留 |
| 纸面 | `#fffef9` | 适合阅读、表单与浮层 |
| 主文字 | `#2d4654` | 蓝灰墨色，方向正确 |
| 操作强调 | `#587493` | 足够克制，应减少同时出现的强按钮数量 |
| 棋盘浅格 | `#eee8d9` | 与白子协调，但需要小尺寸识别验收 |
| 棋盘深格 | `#b1c6c2` | 青瓷灰绿，是当前视觉识别点 |

问题主要在这些颜色如何分配注意力，而非十六进制值本身。建议建立三组同内容对照稿：现状、仅减少容器/调整层级、再局部微调冷暖光。先判断第二组是否已解决问题，再决定是否改色。

## 5. 与 Chess.com / Lichess 的能力比较

Chess.com 官方 Game Review 资料列出了逐步反馈、关键着法、重试及具体想法展示等学习入口；其重点是把分析结果组织成可以跟随的过程。[官方说明](https://support.chess.com/en/articles/8584089-how-does-game-review-work)

Lichess 官方功能页列出了分析棋盘、错误复习、持久化可分享 Studies、开局数据库、个人开局探索和七子残局库等能力；其重要参考价值是研究工具之间的连续性。[官方功能页](https://lichess.org/features)

| 维度 | 当前覆盖 | 真正的差距 |
| --- | --- | --- |
| 导入一盘棋 | PGN、FEN、文件、多棋局、账户同步 | 首次导入后的教学目标、异常解释、角色选择 |
| 快速知道哪里出了问题 | 关键时刻、分类、图表、总结 | 入口重复，概览埋深，部分总结语义错误 |
| 理解为什么 | 结构证据、Stockfish PV、Coach | 通用数值说明多于可视化因果说明；战术 motifs 有限 |
| 自己重试 | 已有原地重试及提示计数 | 进入前可能已看过答案；进度与结束页脱节 |
| 深入分析 | MultiPV、变例、Notebook、Explorer、Tablebase | 候选线操作层级与发现性；Explorer 过滤能力较窄 |
| 长期学习 | 多局趋势、开局/阶段画像、训练队列 | Training 首页偏报告；学习者身份与复习调度不够贯通 |
| 分享与协作 | PGN、PNG、URL fragment、备份 | 不等同于在线协作 Study；跨设备连续性仍有限 |
| 可访问性 | 部分控件命名、快捷键、响应式 | 棋盘读屏名称、完整键盘走棋、对比度与真实缩放 |
| 运行可靠性 | Browser Core 独立、缓存、离线、CI | 真实设备、真实引擎异常与生产运行证据 |

不建议为追求清单相同而立即加在线对弈、社交、课程商城或实时协作。应先把现有闭环做可信。

## 7. 可信度与业务逻辑修复

### C01. 先排查 Opera Game 的可疑评价

**观察：** 本次示例界面把 `15. Bxd7+` 标为 Blunder、Accuracy 约 39、胜率损失约 21.0 个百分点；Study 显示所用引擎标识 `18`、depth 10。后续界面又识别了 `16. Qb8+` 与将杀。

这是一条应优先复核的信号，不应仅凭名局印象断定 Stockfish 或分类公式错误。当前浏览器已有缓存，尚不能区分旧数据、搜索质量、UCI 配对、局面身份或组装问题。

**调查方法：**

1. 在隔离的测试 profile 中导入相同 PGN；不删除用户数据。
2. 固定引擎真实版本、构建、depth、MultiPV、线程、哈希与验证策略，保存每个目标局面的 FEN 和原始 UCI transcript。
3. 分别检查第 28/29/30 ply 的根局面、实走 `searchmoves` 搜索和走后搜索；检查 `info`/`bestmove` 是否属于同一请求。
4. 以同版本独立 Stockfish 对照；回放所有 PV 验证合法性。区别“主线被对手配合后将杀”和“对所有最佳应对强制将杀”。
5. 如果独立评价不同，再定位 worker 消息、取消、缓存、POV、mate/CP、assembler 或低深度验证预算。
6. 若只是旧缓存，应记录它为何仍兼容；若是算法/引擎构建身份变化，应更新相关 cache identity，而非只清空缓存隐藏问题。

**涉及位置：** `packages/stockfish/src/{browser-engine,protocol,cache,game-review}.ts`、`packages/analysis/src/{game-analysis,verification}.ts`、`apps/web/src/lib/analysis-cache.ts` 及 objective orchestration。

**验收：** 同一合法局面和固定配置有可追溯结果；可疑着法在基线/验证/界面上来源一致；需要保留的不确定性在 UI 可见。未定位之前，不为了“让名局看起来漂亮”调 Brilliant/Accuracy 阈值。

### C02. 提前结束不能写“全部已经复盘”

**复现：** 示例打开在起始局面，显示 `5 key moments · 0 seen`；点击 `Finish review early`，出现 `Review complete` 和 `5 key moments reviewed`。

**原因：** `key-moment-navigation.tsx` 的提前结束只把 `finished` 设为 true；`review-completion.tsx` 使用关键时刻总数生成标题，没有收到实际访问集合。

**修复：**

- 分开 `totalMoments`、`seenMoments`、`attemptedPositions`、`solvedUnassisted`、`hinted`、`revealed`、`skipped`。
- 提前结束显示“本次查看了 0 / 5 个关键时刻”，提供继续入口。
- 浏览某个局面只能记为“已查看”，不能自动记为“已学会”。
- 全部查看后可以说“关键时刻已浏览完”；训练掌握程度依据尝试结果另行表达。
- 没有关键时刻时，仍允许结束本次学习，但不能虚构完成计数。

**测试：** 零访问提前结束、部分访问、重复访问、全部访问、跳过、提示后答对、无关键时刻；每种状态标题和计数一致。

### C03. 完成摘要的选材需要明确规则

**当前：** `apps/web/src/lib/review-completion.ts` 在 Best/Great/Brilliant 投影中，仅按 Accuracy 取最大值，相同时保留前者。示例结束页选出了 `4. dxe5`，而不是后面的精彩时刻。`player` 仅影响阶段句子，不过滤最佳/失误候选。

此外，最大失误只要求 critical moment 的损失大于零；一个带特殊注释、损失极小的好棋也可能进入“失误”候选。这是代码层面的边界风险。

**修复：**

1. 显式设置摘要 scope：我方/指定颜色/双方观摩。
2. 我方摘要的最佳和失误都按同一 scope 筛选；双方观摩时给每条事实显示行棋方。
3. 最大失误使用 canonical `quality` 与遗漏注释的明确条件，而不是任意正损失。
4. 最佳时刻建立**教学选材规则**：证据充分的特殊好棋、关键抉择优先，再比较普通高质量着法；同分有稳定 tie-break。
5. 该规则放进 analysis/core 的可测试 selector；不要在 React 中再定义一套着法优劣。
6. 更稳妥的标题可用“值得回看的好棋”，避免把教学选材包装成新的绝对质量等级。

**验收：** 同 Accuracy 的普通 Best 不无条件压过有证据的关键好棋；黑方学习者不会收到未标明颜色的白方“最佳表现”；小幅损失的 Brilliant 不被概括为最大失误。

### C04. 修复确定性 Coach 的统计和表述

**位置：** `packages/analysis/src/coach-facts.ts`，`buildDeterministicGameCoach()`。

**确认的问题：**

- `strongMoves` 累加 `brilliant/great/best/excellent`，却输出“Best 或更高”/“Best or better”。Excellent 不符合该描述。
- 使用 `classificationCounts`，容易把 Book、Forced 等兼容投影与连续质量混为同一统计层；UI 主表已使用 V2 的质量/注释分离。
- 对零损失的 Critical/Brilliant，摘要只写“0.0 个胜率百分点的波动”，没有解释为何值得复盘。
- `confidence: high` 是固定值，易让用户把“模板忠实引用事实”理解为“引擎搜索及教学结论均高度确定”。

**修复：**

- 普通质量统计消费 `qualityCounts`；特殊语义消费 `annotationCounts`。事实 schema 若未传递这些字段，应在共享类型和 fact builder 中增加，不能在 UI 猜测。
- 明确选择“Best 数量”或“Best / Excellent 数量”，文案与集合完全一致。
- 关键时刻根据 canonical 注释生成不同短句：保住唯一合理选择、真实物质投入、错失将杀、明显损失等；证据不足就只描述已知变化。
- 分开展示数据来源、搜索验证状态、文本生成方式；不要用一个 high 覆盖所有置信问题。
- 变更 Coach 内容语义后更新 prompt/cache 版本，避免旧摘要继续出现。

**测试：** Best+Book、Best+Forced、Excellent、Brilliant+Critical、零损失关键着、未验证候选、双语言。统计与 Review 表一致，注释不能导致重复计数。

### C05. 明确阶段指标口径

**当前：** Review 使用 canonical `phaseAccuracy`；Training 的 `phaseProfiles()` 对该阶段各步 `move.accuracy` 取算术平均。`advanced-study-page.tsx` 直接把 `profile.averageAccuracy` 作为阶段卡的大数字。

本次同一黑方样本，Review 的 Opening/Middlegame 显示约 86.0/56.4，Training 的阶段卡约 90.2/89.7。不同口径可以产生不同数字，但必须让用户知道它们不是同一个量。

**推荐修复：**

- 如果 Training 主卡要叫“阶段 Accuracy”，使用 canonical 单局阶段 Accuracy 的明确跨局汇总，标明局数和权重。
- 如果保留逐步算术均值，命名“平均单步 Accuracy”，作为辅助指标；不能默默替代 canonical phase Accuracy。
- 区分全局平均、最近样本、每步加权和每局等权。给 `metricId`、`aggregation`、`sampleGames`、`sampleMoves` 留机器可读字段。
- 一局、极短阶段、缺失阶段、不同局长和低覆盖样本都要有明确规则；不能用零代替缺失。

**验收：** 同一局的 canonical 阶段数值能在两个页面对上，或页面明确解释为何不是同一指标。此次若改聚合语义，必须更新 `advanced-study-v2` 相关版本/文档和回归 fixture，不动单局 Lichess 兼容公式。

### C06. Moves 页面 Hook 顺序风险

**位置：** `MovesRoutePanel()`，`apps/web/src/components/review-route-panels.tsx`。

当前 `if (!analysis) return ...` 在 `useMemo()` 之前。同一组件从无分析进入有分析时，会改变 Hook 调用数量。这是 React Hook 规则风险；本次没有重现该切换导致的崩溃，不应写成“所有 Moves 页面必崩”。

**修复：** 把 Hook 放到条件返回之前并处理空值，或把有分析的面板拆成单独组件。

**测试：** 在分析未完成时进入 Moves，随后分析成功、取消、失效、重新分析；不能出现 Hook 顺序错误。`eslint.config.mjs` 当前未启用 React Hooks 规则，应补合适的 lint 覆盖；lint 通过不能证明这一项安全。

## 8. 复盘主流程与学习闭环

### U01. Review 需要更明确的主任务

桌面实测同时出现“从关键时刻开始”、Study 链接、整组错误练习入口、关键时刻前后导航、提前结束和完整 move list。当前着法判定、Why、候选线、Game Summary 则位于棋谱之后。

**问题不是缺少引导，而是引导相互竞争。** 右侧即使有留白，也未必让人知道下一步做什么。

**推荐布局：**

```text
桌面
┌ 棋盘与双方信息 ──────────┬ 当前学习任务 ─────────────┐
│                         │ 当前着法 / 关键时刻进度    │
│                         │ 一句有证据的说明          │
│                         │ 主要动作：自己试 / 下一处  │
│                         │ Why / 查看变化（次级）     │
│                         │ 紧凑棋谱                  │
│                         │ 本局概览入口              │
└ 棋盘导航 ────────────────┴──────────────────────────┘
```

- 保留 Review/Moves/Study 的现有路由；Review 的棋谱只提供上下文窗口，完整浏览属于 Moves。
- 当前着法说明放在候选线和长列表之前。
- Review 默认主动作是“下一处关键时刻”或“自己试”；批量错误练习是次级入口。
- 概览不应被完整长棋谱和多条 PV 挤到不可发现的位置。可用紧凑 Accuracy/错误摘要入口，不必把完整图表常驻。
- `Finish review early` 放进进度操作或次级菜单；保持可用，但无需一直占一整行。
- 手机按“棋盘 → 相邻导航 → 当前任务 → 解释 → 完整列表”的顺序组织，避免看解释时完全失去当前局面上下文。

**验收：** 新用户进入已分析棋局，能在 5 秒内指出下一步；常见笔电尺寸中无需滚过完整棋谱才能看到当前着法原因。该目标是建议的验收标准，并非本次已测结果。

### U02. 引导进度要有稳定归属

当前 `visited`、`finished` 属于 KeyMomentNavigation 的局部 state，路由切换卸载后不保证保留。棋盘保持原位，不等于学习进度也保持。

**修复：** 放进稳定 review session，按 game identity + objective analysis identity 归属；跨 Review/Moves/Study 保留。是否跨刷新保存可通过轻量 session 持久化完成。重新分析后仅合并仍有效的 ply 身份；不能把旧版本完成进度无条件套到新结果。

**验收：** 看两处 → Study → Review，进度不丢；刷新后按定义恢复；换一盘棋不串；重分析新增关键时刻后不错误显示完成。

### U03. “自由分析”与“先试后看”应有明确边界

已有练习锁定逻辑会隐藏答案，这是重要基础。问题在进入之前：Review 通常已有引擎箭头和候选线；后来再显示“try it before the answer”不能保证用户没看过答案。

**修复：**

- 引导模式到达待训练局面时，先呈现走前局面和任务，答案由用户揭示。
- 自由分析模式保持现有探索能力；从已揭示答案进入练习时标明“回顾练习”。
- 记录 `answerExposed`，与 `hinted/revealed` 一起影响学习记录，不修改客观棋步标签。
- 隐藏范围包含箭头、PV、图表提示、可访问名称、Notebook/导出入口中的答案；复用现有 `practice-presentation`，不要散落条件判断。

**验收：** 鼠标、键盘、触屏、读屏下均不泄露未揭示答案；退出练习恢复原局面/分支/箭头设置。

### U04. Why 应解释证据，不只打印规则

当前 Why 展示 precedenceRule 文本替换、Win% loss、Accuracy、前后评价及 annotations。Moves 还提供 rank、verification、exclusions，但对一般用户仍接近诊断数据。

**修复结构：**

1. 一句解释：这步保住优势、丢失多少胜率、或为什么是关键选择。
2. 一个棋盘动作：查看对手回应/比较另一着。
3. 可展开证据：深度、MultiPV gap、牺牲、立即回收排除、验证状态等。
4. 深层诊断才显示内部枚举和缓存身份。

文案必须由 canonical evidence 映射；不能仅看一个分数就编出“露王”“丢后”“双攻”。

**验收：** Brilliant/Critical 的 Why 能回答标签原因；普通失误能区分已知后果与未知原因；解释箭头来自合法验证线。

### U05. Study 先提供可用的学习动作

本地服务离线时，实测 Study 开头集中显示 Generation status、Local coach unreachable、Ollama、语言、Configure，再显示“Build whole-game study”。生成后出现 deterministic/canonical-facts/high confidence 等技术信息；中文内容中仍大量夹杂英文区块标题和 `Ply 19`。

**修复：**

- 首屏标题围绕“这局最值得学的一点”或“生成本局总结”。
- 降级状态说“可使用本地棋局事实生成总结”；技术失败细节放进来源说明。
- 把完整的用户动作保留为主按钮，不把正常可用的 fallback 做成失败页面。
- 用 `10. Nxb5` 取代 `Ply 19` 等内部计数；行棋方明确。
- 学习文本、区块标题、按钮按选定语言协调；短期保留英语主 UI 也应在中文教学区域保持完整中文。
- 低证据时明确提供“数值概览/建议检查项”，避免通用模板给人已经提供个性化深度指导的错觉。

**验收：** 不安装本地服务的用户也能完成可理解的学习任务；来源信息可找到，但不会先要求用户理解服务架构。

### U06. Training 应从“报告入口”变成“训练入口”

当前默认首屏以 Player、Scope、Overview/Rating/Openings/Middlegame/Endgame/Mistakes/Highlights/Plan/Coverage 组织内容。这适合画像分析，未必回答“我现在练什么”。

**修复：**

- Training 首屏先显示继续上次、可练局面数、一个推荐动作。
- 画像分析保留在明确的次级分区；不要删除已有深度工具。
- 数据不足时提供直接可做的任务，例如本局错误回顾，不只要求继续收集样本。
- 每条任务说明来源、目标和完成条件。
- 现有队列是按证据局面记录查看进度；长期掌握度应另设间隔复习和再次尝试状态，不能把“已查看”当作能力提升。
- 复习调度与 Stockfish 客观数据分层；调度允许时间依赖，客观分析不能因此改变。

**验收：** 首次、无任务、有进行中任务、任务完成、源棋局缺失、低样本均有正确主动作；用户无需先理解九个报告栏目。

### U07. 结束页要能把本局问题直接送入训练

实测结束页显示“本局尚无局面加入 Training”，随后只有通往通用 Training 的链接。`useTrainingCount()` 当前统计的是包含该局 evidence 的队列 item 数量，文案却称 position 数量；一个 item 内可含多个局面，计数会失真。

**修复：**

- 直接提供“把本局这 N 个局面加入训练”，展示将加入的对象。
- 区分任务数和去重局面数；局面用现有 `gameId:ply` 身份，不能用 item 数量代替。
- 已加入、已完成、部分加入、写入失败分别处理，操作幂等。
- 从结束页进入 Training 时携带 player/game scope，直接落在对应任务，而不是重新选择画像。

**验收：** 一个任务含三个本局局面时显示三个；重复加入不重复；混合来源任务只统计本局；提示/揭示记录不转成无提示解出。

## 9. 可读性、无障碍与视觉完善

### A01. 空气感不能依赖低对比功能文字

根据当前 token，用标准相对亮度公式计算：

| 前景 / 背景 | 对比度约值 | 处理 |
| --- | --- | --- |
| `#829096` / `#f8f6ef` | 3.04:1 | 不适合普通小号功能文字 |
| `#829096` / `#fffef9` | 3.26:1 | 同上 |
| `#5f747d` / `#f8f6ef` | 4.54:1 | 勉强达到普通文字阈值；还需检查实际混合背景 |
| `#587493` / `#fffef9` | 4.80:1 | 当前组合可用 |

`--ink-faint` 被用于输入 placeholder 和部分 quiet move 小字等功能场景；Settings/History/平台信息仍有较多 11px 文本。11px 本身不等于违反标准，但长时间阅读代价偏高。

普通文字最低对比度通常为 4.5:1，大字及豁免情况应按实际用途判断，不能把所有品牌/禁用文字都算成违规。[W3C 对比度说明](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)

**修复：**

- faint 仅保留给真正装饰；功能性小字使用通过实际背景计算的 text token。
- 主要说明建议 14–16px，紧凑数据 12–14px；这些是产品建议，不是 WCAG 法定字号。
- 通过减少重复文案腾出空间，而非把字体全压小。
- 检查 active/hover/focus、错误提示、输入帮助和真实渐变/opacity 合成后的结果。
- 点击区域继续复用已修复的 row/link 规范。WCAG 2.2 AA target-size 的基准是 24 CSS px 并有例外；触屏主要动作建议约 44px，不能把两者混称。[W3C 目标尺寸说明](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)

### A02. 棋盘读屏与键盘走棋是独立验收项

本次可访问树中有多个没有名称的棋子按钮/拖动项；Feather 图片使用 `alt=""`，若外层未提供棋子和方格名称，读屏用户无法理解目标。当前上一步/下一步快捷键，不等同于能通过键盘输入一着棋。

**修复：**

- 为交互方格/棋子提供“白马 g1”“空格 f3”等语义，不要让图片和容器重复朗读。
- 提供棋盘内的方向导航、选择、确认、取消及升变操作；或提供经过 chess-core 验证的 SAN/UCI 输入作为等效入口。
- 棋盘快捷键和全局复盘快捷键明确区分焦点范围。
- 对选中、非法着、将军、完成升变进行适量 live announcement。
- 只读/练习隐藏状态也必须能理解，并避免通过 accessible name 泄题。

**验收：** 完全不用鼠标完成导入、逐步复盘、走一条变例、升变、撤回和一次练习；再用 VoiceOver 和 NVDA 验证。当前观察足以要求补测，但不能宣称所有读屏环境都完全不可用。

### A03. 关键时刻图标不能统称 Critical

`review-presentation.tsx` 的摘要列表向 `QualityIcon` 固定传入 `title="Critical"`。实测 Mistake/Blunder 条目的可访问名称也带 Critical，与棋谱的错误名称不同。

**修复：** 容器叫 Key moment，图标名称保留实际 classification/annotation；如为了强调关键抉择显示 Critical 注释，仍明确保留基础质量。所有视图应区分“关键时刻集合”和“Critical 好棋注释”。

**验收：** 错误条目读作 Mistake/Blunder，Critical 好棋读作 Critical；board/list/summary/export 对同一事实不冲突。

### V01. 把空气感落实到注意力与节奏

**当前优点：** 已减少玻璃拟态，暖纸、细线、少量洗色统一；复盘棋盘成为稳定中心。

**剩余问题：** 右侧连续的操作区、分隔线、宽按钮与长列表，让阅读节奏仍像管理面板。首页的大标题和表单容器较完整，但与复盘的高密度文字感有距离。

**修复：**

- 在现有 token 内先做组件层级：主任务一个，次级动作收束，诊断按需。
- 只保留有意义的纸面层：表单、总结、真正浮层；日常信息用清晰行距和分组。
- 设统一的 section gap、row gap、标题比例和行长，不逐页凭感觉调。
- 交互动效表达状态变化，保留 reduced-motion；不做背景常驻动画。
- 声音只由棋盘操作触发，错误/提示不使用夸张奖励声；继续尊重现有静音偏好。
- 颜色微调采用同内容 A/B 视觉审查，不改变错误、Stockfish、Maia 的语义映射。

**验收：** 关闭所有装饰性元素后任务仍然清楚；仅用灰度看也能识别主动作、当前状态和错误。

### V02. 棋子要以识别实验验收

v1.1 已明显强化 K/Q/B 角色；当前不应再次整套重绘。白子亮部与浅格仍需要在小尺寸、低亮度、非 Retina 和触屏环境下验证。

**方法：** 让不熟悉本项目的棋手在 32/40/48/56px 和真实局面中辨认角色/颜色，记录误认类型和时间；覆盖双方兵群、残局、重叠箭头、升变和质量 badge。

**修复顺序：** 只修出现证据的轮廓、明暗或边缘；保持原有羽毛细节作为次级纹理。Classic 入口保持可发现；不要用更浓的背景补偿所有棋子识别问题。

### V03. 内容设计需要一个统一词表

集中处理：Review/Study/Training/Notebook 的用途、Critical 与 key moment、质量与注释、WinPercent 与 Maia WDL、局数与局面数、已看与已解出、模型离线与功能不可用。

当前 `Grounded by 18 depth 10`、`canonical-facts`、`Ply`、内部规则字符串属于需要转译的例子。技术值保留在详情，但主层用能理解的名称。

**语言策略：** 先把英语 UI + 中文教学的边界做好；如果目标用户包含中文/日文用户，再独立推进完整 i18n。不要只替换零散按钮形成三语混杂。

## 10. 研究能力、个人身份与训练语义

### P01. Explorer 是已有功能，需要完善而非重建

当前 `OpeningExplorerPanel` 已有 All players / Masters、样本、WDL、来源、缓存时间和陈旧结果标识。与个人研究工具相比，仍缺少界面上的等级/时限/个人样本过滤；错误状态提供文本，但没有同等明确的本面板重试动作。

**建议：**

- 第一阶段补重试、来源切换状态、当前 FEN 与样本口径说明。
- 第二阶段按实际用户需求增加 rating/time-control 过滤；参数必须进入请求验证和缓存键。
- 个人开局统计优先消费现有本地库，再考虑外部个人 Explorer。
- 不把高频着法等同于最佳着法，也不把人群数据库频率等同于 Maia 概率。
- Tablebase 同样保持独立理论结果、DTZ/规则语义与来源说明，不反向替换已存的历史 Stockfish 分类。

**验收：** 快速切换局面不串结果；空样本/断网/限流有恢复动作；不因一条 explorer 请求失败阻断复盘。

### P02. 战术解释的能力边界需要诚实呈现

`docs/move-classification.md` 明确当前 `motifs` 只有 sacrifice，generic miss 无完整战术检测器支持。`buildDeterministicGameCoach` 却从 blunder 等分类推导“严重战术节点”。Blunder 本身不能证明原因必然是某种战术。

**修复分两层：**

1. 立即修文案：有失误证据就说“严重失误/胜势遗漏”，战术扫描作为一般建议，不冒充已检测原因。
2. 后续增加有限、可验证的主题检测：例如吃到未保护子、将杀威胁、双攻等；每个 detector 有定义、正反例、证据方格及适用边界。

这些检测属于 `packages/analysis`，输出结构事实后再交给 Coach。不要让 LLM 自行发明动机，也不因为 detector 新增就顺便调整 Brilliant/Great。

### P03. 统一“正在帮助谁”

当前完成摘要的 player 来源是 `preferredOrientation`，该字段至少不应被当作唯一学习身份；Training 首次进入还可能选到样本中的对手。本次示例进入 Training 默认是 Duke，而不是 Morphy。这不一定是错，但如果上一页正在练白方，跳转没有延续目标就会打断任务。

**修复：**

- `boardOrientation` 只负责朝向；`practiceColor` 负责练习范围；`learnerIdentity` 负责跨局个人画像。
- 明确“分析双方/我执白/我执黑”；平台确认身份可辅助默认值，手动选择仍保留。
- 结束页、Study、训练任务传递同一学习目标；翻转棋盘不会切换学习者。
- 观摩名局时不强行把任何一方说成“你”；手动导入无身份时允许匿名学习。

**验收：** 白方复盘 → 翻转棋盘 → Study → Training，学习者不变；切换学习者后统计和建议同步更新，旧 Coach 适用范围明确。

## 11. 运行、数据与发布质量

### R01. 补齐证明成熟度的测试

现有 CI 已覆盖默认流程集，并且有单独 Browser release 套件，不能说“没有集成测试”。但仍有几处边界：

- `visual.spec.ts` 因 macOS 基线在 Linux 流程中被排除；需要独立、稳定平台的视觉校验，不能只留本地文件。
- `zoom-acceptance.spec.ts` 通过缩小 CSS viewport，另加文档 CSS zoom 验证布局。这是有价值的近似测试，但不等同于真实浏览器缩放、系统字体缩放、DPR 和输入坐标的全部组合。
- 文档仍把低端设备解码、真机、部分生产/认证场景列作外部 gate。

**补充验收矩阵：**

| 场景 | 必须覆盖 |
| --- | --- |
| 桌面布局 | 1280×720、1366×768、1440×900、1920×1080；长名、长 PGN、空状态 |
| 缩放 | 浏览器原生 125/150/200%，系统文本缩放；升变/弹层/点击坐标 |
| 手机浏览器 | iOS Safari、Android Chrome；320/360/390/430 宽度、软键盘、旋转、安全区 |
| 输入 | 鼠标、触摸、纯键盘、VoiceOver/NVDA |
| 引擎 | 真实 Worker/WASM、取消、重试、缓存命中/失效、将杀/无合法着 |
| 异步 | 分析中切路由、快速换局面、重分析、后台标签恢复 |
| 断网 | 缓存可用/不可用、Explorer 降级、Coach 不可达、离线导入导出 |
| 存储 | quota、损坏缓存、备份恢复冲突、多标签并发、浏览器驱逐 |
| 生产 | HTTPS、OAuth、真实代理头、回滚、错误日志和版本可追踪 |

**性能建议指标：** 用户交互到可见反馈、首个可用分析、整局完成时间、峰值内存、取消响应、长列表响应。分别记录设备、局长、深度、热/冷缓存。先建立基线，再约定预算；本次没有性能测量，不能给出虚构的毫秒成绩。

棋子总资源约 934 KB 是已有文档的测量，不是本次重测。不要把“PNG 压缩已经试过”解释为所有网络/解码性能已解决；可另评估派生尺寸/格式，前提是保持 alpha、跨端和导出一致性。

### R02. 本地优先能力需要可理解的恢复路径

已有 IndexedDB、备份、分享链接及 PNG/PGN 导出是优势。需要用户知道：数据存在哪、什么随分享出去、换设备后如何继续。

**修复/验收：**

- 首次成功保存给轻量说明；存储失败必须显式反馈并提供导出，不能假装已保存。
- 备份恢复展示预览、冲突策略和完成统计；验证分析、Notebook、训练进度之间的引用。
- 长 PGN 超出链接预算时直接指向文件导出；分享链接中的 base64url 不是加密。
- 本地分享不是多人实时协作 Study；UI 不应造成这类预期。
- 导出长名字、非 ASCII 字符、黑方视角、FEN 和离线素材失败需可读且一致。
- 云同步/协作作为 P3 独立产品决策，需要身份、权限、版本冲突与运维预算，不属于换 UI 即可完成的项目。

## 12. 推荐实施分批

### 批次 A：事实与状态可信

范围：C01 调查，C02–C06，A03，U07 计数修复，P02 文案修复。

交付：

- 可疑引擎结果的可复现记录或已定位结论。
- 结束状态不夸大，计数正确，学习对象明确。
- Coach 使用清楚的 V2 口径；阶段指标有明确名称。
- Hook 顺序修正和针对异步切换的回归用例。

此批不做整页重设计。若修改算法或语义，更新对应文档和版本，并按项目技能补真实 fixture。

### 批次 B：Review 学习任务收束

范围：U01–U05、P03。

交付：一个清楚的关键时刻主流程、稳定 session、先试后看、当前着法证据靠前、正常可用的 Study fallback、明确学习者。

退出条件：新用户可以完成一次完整复盘，且没有进度丢失、错误完成声明或答案泄露。

### 批次 C：长期训练闭环

范围：U06–U07、P01 基础恢复。

交付：结束页一键加入本局训练、任务数/局面数一致、Training 首屏直接开始、原有报告保留、Explorer 重试。

间隔复习可作为 C2 子批次；不要把队列架构重写和统计修复混在同一个变更中。

### 批次 D：视觉与无障碍精修

范围：A01–A02、V01–V03。

交付：阅读尺度、token 用途、跨页 spacing/文案、读屏棋盘、棋子识别实验。主题整体保持 Windowlight，局部调色须有同内容比较证据。

### 批次 E：真实发布验收

范围：R01–R02 和前三批回归。

交付：可追踪的版本、真实设备矩阵、性能基线、备份恢复演练、生产 smoke 与回滚记录、稳定视觉 CI。

**依赖：** A → B → C；D 的对比度/无障碍可与 B 分开推进，但视觉定稿应基于最终信息架构；E 贯穿各批并在发布前收口。没有做完 A，不能仅凭 D 的截图宣布“最终完善”。

## 13. 关键回归用例清单

| 用例 | 预期 |
| --- | --- |
| 0/5 关键时刻提前结束 | 显示实际访问 0/5，不显示全部已复盘 |
| 已看两处，切 Study 再返回 | 仍是两处；board cursor 与 session 不冲突 |
| 普通 Best 与 Brilliant 同为 100 | 教学摘要按明确规则选材，不只先到先得 |
| Critical 好棋有 0.2 点损失 | 不因此自动叫“最大失误” |
| 黑方学习者、白方有最大失误 | 我方摘要不会错误归因；双方摘要明确颜色 |
| 一任务包含三处本局证据 | 训练显示三个局面而非一个 |
| Best 同时 Book/Forced | 质量数量与注释数量分开，Coach 与 Review 一致 |
| 只有 Excellent | 不写 Best 或更高 |
| Critical/Brilliant 无胜率损失 | 解释其关键证据，不只输出 0.0 波动 |
| 无分析进入 Moves，后台完成 | 没有 Hook 顺序错误，界面正常更新 |
| 同一局打开 Review 和 Training 阶段 | 数字相同或指标名清楚区分聚合口径 |
| 翻转棋盘 | 不改变学习者和任务所属颜色 |
| 已经看过最佳线再开始练习 | 标明回顾练习，不计无辅助首次解出 |
| VoiceOver 到棋盘方格 | 能获知坐标、棋子、状态，隐藏答案不被朗读 |
| Explorer 失败后重试 | 不重载整局，保留棋盘与已有可用分析 |
| 恢复旧备份 | 不把旧 Coach/算法/训练记录误认为当前兼容结果 |
| 真实浏览器缩放后升变 | 所有选项可见可点、焦点可恢复 |
| Opera 可疑局面隔离重算 | 保存完整来源，能够解释缓存/引擎/验证之间的差异 |

## 14. 完成标准：什么时候可以说“达到了目标”

### 美学通过

- 保持原创 Windowlight/Feather 识别；不同页面看起来是同一个产品。
- 轻盈来自层级、留白与反馈克制，而非小字、低对比和隐藏操作。
- 用户长时间读棋时，棋子、当前局面和下一动作仍能立即识别。
- 官方参考被转译为产品语言，不依赖电影贴图或装饰堆叠。

### 复盘体验通过

- 首次导入者无需解释即可找到关键时刻、自己尝试、查看原因并完成。
- 当前局面、已走着法、下一候选线、分支、练习状态不会混淆。
- 结束摘要和训练计数可核对，学习者身份贯穿。
- 断网、服务缺失和缓存失效有明确、可恢复的行为。

### 业务与工程通过

- 关键事实都有 canonical 来源；统计与文案一致。
- 同一个指标不在两个页面悄悄换算法。
- 新回归测试覆盖本次发现；真实设备、真实引擎、真实缩放和发布流程有记录。
- 明确区分“可用于日常复盘”“生产发布已验收”“完整在线平台”三种声明。

建议最后邀请 5–8 位不同水平、未参与开发的棋手进行观察测试，含至少两位手机用户；记录卡住的步骤、错误理解、是否学会一个改进点。该样本用于发现问题，不足以宣称统计显著的学习效果优于竞品。
